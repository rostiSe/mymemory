## Key conventions

### Routes belong in app/ only
Never co-locate components, stores, or utilities inside `app/`. This is an Expo Router anti-pattern. The `app/` directory is for route files and layouts only.

### One Supabase client instance
`src/lib/supabase.ts` exports a single client. Import it everywhere. Never create multiple instances.

### One MMKV instance
`src/lib/mmkv.ts` exports a single MMKV instance. All Zustand stores with persistence use this instance.

### Zustand stores are domain-scoped
One file per domain: `auth.store.ts`, `ui.store.ts`, etc. Never one giant store file. Each store exports its own hook and persist config.

### tRPC procedures are the only way to talk to the backend
No direct database calls from the Expo app. All data goes through tRPC procedures. This keeps the server/client boundary clean.

### Types live in types/index.ts
Shared types that don't belong to a specific feature. Feature-specific types live next to their component or store.

## CLAUDE.md template for Expo projects

```markdown
# CLAUDE.md — [Project Name]

## Stack
- Expo Router (file-based routing)
- TypeScript strict — no `any`, no `as` casts without comment
- NativeWind v5 + Tailwind v4 — token classes only, no raw values
- Zustand + MMKV — one store file per domain
- tRPC + Hono — all data fetching via tRPC procedures
- Supabase + Drizzle — database layer
- Supabase Auth + expo-secure-store — auth

## Rules
- Routes belong in app/ only — never co-locate components there
- Always use path aliases (@/*) over relative imports
- Never use raw hex, px, or arbitrary Tailwind values — use token classes only
- Never create multiple Supabase or MMKV instances
- Always handle loading and error states in every screen
- Use kebab-case for file names: user-profile.tsx not UserProfile.tsx
- Always test on both iOS and Android before marking a ticket done
- Expo Go first — flag immediately if a change requires a dev client rebuild

## Ticket workflow
1. Read the ticket file at the start of every session
2. Restate the goal and ask clarifying questions before writing code
3. Mark ticket as in-progress
4. Build, verify acceptance criteria, mark done
5. Never start the next ticket without explicit instruction
```
